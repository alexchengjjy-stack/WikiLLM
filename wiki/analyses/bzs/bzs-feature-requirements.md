# 好好簽 (BZS) 企業需求與功能分析 (Feature Requirements)

> 透過對台灣各大垂直產業（醫療、不動產、教育等）的客戶畫像痛點剖析，可反向推導出企業在實際導入電子簽章時，會檢視的 5 項「剛性功能需求」：

### 1. 深度 API 整合與 Webhook 回寫機制
超過 80% 的中大型客戶不滿意「純 SaaS 介面」。他們要求 BZS 將狀態（如用印人、時間、簽署完成的 PDF 檔案）即時回寫到他們內部的 ERP、BPM（如鼎新）或病歷系統。這種**「無頭化 (Headless)」或「微服務化」**是成交關鍵。
此外，進階需求不斷湧現，例如：**「公開表單 API 化與 AATL 支援」**（聯合線上要求，因目前外部表單未支援 AATL）、**「多次簽名暫存後再一次 AATL 封裝」**（采盟數位要求），這挑戰了原本標準化的簽署狀態機。

**大企業導入的本質阻力**：以「育達補習班」為例，他們雖然需要電子簽章，但完全不想改變現有業務流程去登入一個獨立的 SaaS 平台。對這類大型客戶而言，獨立 SaaS 的推廣阻力極大，**「無縫 API 嵌入」才是唯一的終極解方**，這進一步證實了 API 中台化的重要性。另外，為了讓好好簽與內部員工系統整合，並將登入帳號改為員工編號，育達提出深度整合需求，好好簽則提供 API 方案（年費 10 萬元以上，AATL 與簡訊按量計費，不限人數）。此外，針對內部簽核流程，越來越多中小企業（如龍邑不動產）提出對**「Power Form (內部表單，如請款單)」**的強烈需求。

針對企業內部工作流，客戶更要求系統具備 **SLA (Service Level Agreement) 監控設定**與**逾時催辦 (Escalation)** 功能，讓節點停留逾時能自動發出提醒。同時，BZS 也預計於 Q2 底完成**「合約歸檔管理功能」**的開發，以滿足精誠等整合商的專案需求。

**2025H2 公開表單與 Webform 流程決策**：在「龍巖股份有限公司」的服務車單派車場景中，由於最底層的服務司機通常沒有 Email、手機 OTP 或 LINE 傳簽所需之稽核帳號，造成兩階層簽署（龍巖承辦人 -> 協力廠商承辦人 -> 服務司機）的流程中斷。協力廠商承辦人不得不透過手動複製簽署連結轉發給司機簽名，導致系統缺失司機的稽核軌跡。好好簽對此評估，建議客戶改用「Webform (Google表單) 搭配好好簽後台自動化流程」或採用「現場簽」之替代方案，以確保稽核軌跡的合規與安全。

### 2. 通訊管道的絕對在地化 (SMS / LINE)
台灣本土企業（尤其對 B2C 面向）無法依賴 Email。**「批次發送簡訊任務」**以及**「單向擷取連結轉發至 LINE」**是必備功能。更有客戶要求「BZS 不用發送通知信，只要吐出連結讓我們自己的系統發送」，以此節省簡訊加購點數。
此外，針對高齡者等數位弱勢群體，客戶（如護理之家）強烈要求 Line 傳簽的「手機欄位改為非必填」，以降低簽署阻力。
**第三方簡訊平台串接之技術與效能考量**：育達補習班因簡訊點數儲值具有 1 年到期限制，且內部請款流程不便，曾強烈希望能串接他們配合的簡訊發送商 every8d。但好好簽評估在數發部當時的審核機制下，every8d 的簡訊驗證碼發送延遲高達 10-20 分鐘，可能嚴重影響簽署體驗，因此拒絕此客製需求，堅持維護自建簡訊平台。

### 3. 動態身分驗證與零成本 OTP
系統自帶的 OTP 通常需要額外計費（約 NT$2/則）。許多大客戶希望支援**「客製化身分驗證」**，例如使用系統自定義的變數（如：買方的手機末三碼、身分證字號）作為解鎖 PDF 的密碼，繞過簡訊計費機制。
**加值簡訊點數管理與主動提醒機制**：由於簡訊儲值有 1 年期限，且點數不足會導致發送失敗，客戶強烈要求系統在「簡訊點數餘額低於一定數值時主動寄信通知」，以及「簡訊點數到期前 1 個月寄信提醒」，避免交易中斷（育達補習班案例）。

### 4. 低阻力的證據保留機制（錄影 / 軌跡）
「聲明錄影」是好好簽的最大賣點之一，但實務上面臨兩難：
- **使用者體驗面**：不動產買賣客戶反饋完整錄影流程過長，妥協要求「僅在寫下簽名那幾秒開啟鏡頭並截圖」即可。
- **法院證據力面**：在金融本票違約爭議中，法院指出僅有「人臉+聲明文字」的錄影屬於**間接證據**，若要有強制執行力，必須錄下**「人臉+用戶簽字過程的筆跡」**作為**直接證據**。這迫使服務商必須重新評估錄影機制的技術架構。
而在輕量級應用（如租車合約），客戶雖然不想用聲明錄影，但因為「公開表單」無法保留簽署軌跡，因而轉向使用「Line 傳簽」以確保雙方皆有完整的稽核軌跡紀錄（豐盛富足資產案例）。

**2024H2 新增洞察**：移工與外籍人士市場（如老頑童通訊行辦理預付卡）有強烈的防詐騙合規需求，必須面對面且錄影簽署。但系統內建的聲明錄影文字缺乏「多國語言 (如印尼、泰國、菲律賓語)」支援，這成為切入移工市場的一大痛點。

### 5. Word 文件直接編輯與預覽
不動產代銷與小型廣告公司（如佶星廣告）反映，目前「必須先在外部編輯 Word 再轉 PDF 上傳」的流程存在斷點。客戶強烈希望能在 BZS 平台上直接上傳 Word 檔並進行即時內容修改、欄位套印，以滿足房屋買賣合約中頻繁變動的成交細節需求。

### 6. 高效的範本管理 UX
隨著企業使用場景複雜化，單一帳號下往往累積大量範本。客戶（如醫療與租賃業）強烈要求導入**「常用範本標籤」**或置頂排序功能，以解決在一頁頁範本清單中尋找特定合約的痛點。

### 7. 大檔案支援與數位憑證合併限制
醫療與照護等產業因為經常需要掃描大量紙本文件，單一 PDF 經常達 27~28MB，超過目前系統 10MB 的單檔限制，這成為了「大檔案上傳」的剛性需求。另外，多數使用者存在觀念落差，誤以為多份合約一次簽署完後可以「合併成單一 PDF 下載」，但不理解每份文件因為各自嵌入獨立的數位憑證 (AATL)，在技術上無法合併。這需要透過 UI 提示或提供批次下載 (ZIP) 功能來彌補。

**2024H2 批次與文件優化實務 (以育達補習班與德軒企業為例)**：
- **批次發送防呆與性能放寬**：補教業大批次發送的需求多樣。系統為此將批次匯入的 Excel 限制由 50 人放寬至 200 人，並修正了發送成功後自動返回前頁的流程，防止使用者因無成功提示而「重複點擊發送鈕」。
- **批次發送失敗清單快捷化**：以往批次發送（如簡訊）若有部分失敗，發起人必須逐筆點擊確認。系統規畫新增「傳送失敗清單」快捷選項，以利快速查閱，但基於號碼/信箱填錯可能，暫不開放一鍵重發。
- **證件圖片上傳的 PDF 內嵌最佳實務**：在德軒企業租約案中，客戶原以「附件」方式上傳證件影本，好好簽建議改用「圖片」屬性，使得證件影本可直接內嵌並於開啟 PDF 時顯示，免去額外下載附件的 UX 中斷。
- **合約與附件批次下載 UX 斷點**：在房屋租賃業（鄭仲亨先生案例）中，下載已簽署合約時，系統只下載 PDF 本身，不會一併下載租戶上傳的「證件影本夾檔」，導致客戶必須逐筆點擊合約去手動下載，極為耗時。為此，系統重整規格，支援下載合約時一併打包下載關聯附件。
- **下載檔名繼承新任務名稱**：客戶反映下載已完成合約時，PDF 檔名仍然顯示原始範本標題（如「房屋租賃合約書範本」），而非發起任務時編輯後的新任務名稱（如「租約-王大明」），導致客戶下載後必須手動一個個改檔名，此 UX 缺陷已由 Kevin 調整規格安排開發。
- **發起任務 PDF 數量放寬**：在季灃健康服務的實際使用中，由於一筆任務除了主要的健康管理報告外，還需同時檢附 4 份相關報告（共 5 份 PDF 檔），希望避免將附屬報告放在單一 PDF 內下載時不方便的痛點。好好簽召開會議後決定，統一放寬「企業方案」發起任務時允許上傳 PDF 的數量上限為 5 份。

### 8. 系統穩定度、SLA 承諾與技術邊界
由於 API 高度依賴，好好簽在日報中曾發生防火牆 (WAF) 誤報導致系統短暫 403 錯誤的事件，以及 Load Balance 切換 Image 造成的 503 錯誤。大企業客戶因此強烈要求「備援機制 (Active-Standby)」、「測試機與正式機的獨立更版流程」，並要求維護時間必須在凌晨進行。

另外，在與「國立臺灣大學」的測試中發現了**系統技術邊界問題**：客戶上傳的 PDF 若包含系統不相容的特殊內建字型，會直接導致系統處理 Timeout。這類隱藏的技術限制已列為 Product Constraint，需於前端 UI 給予明確錯誤提示，或由後端進行字型替換處理。

**2024H2 歷史事件回顧**：
- **AATL 憑證中斷事件**：中華電信 AATL 憑證元件因與 Azure 升級衝突，導致系統半天無法上傳文件。此事件引發客戶強烈客訴（因官網無異常公告且假日客服不通）。此一技術邊界與 SLA 事件突顯了 SaaS 服務必須建立「主動異常推播機制」與「緊急維護公告」的重要性，也是 2B 產品的致命防線。
- **中文輸入法與 Web 相容性**：曾出現「中文輸入法組字狀態卡住欄位無法送出」的 Bug，顯示了在 Web 網頁與系統輸入法的相容性挑戰。
- **高齡化 UX 邊界**：客戶反饋年長者使用手機瀏覽器 (Android/iOS) 簽署時，習慣將畫面放至最大，這會直接導致系統當機。
- **資安合規進度延遲致命傷**：台灣奇恭 (GiGO Taiwan) 原本預計導入企業方案，但因為好好簽當時針對 ISO 27001 的認證時程沒有給予明確答覆（日本總公司之要求），導致該高價值客戶在測試 Docusign 之後直接簽訂 DocuSign 年約，且後續因「中途撤換會造成內部混亂」為由拒絕好好簽的免費補償，顯示出合規時程對爭取外商與大企業訂單的關鍵性。
- **簡訊 OTP 自動帶入與瀏覽器相容性 Bug**：育達補習班反映，在 iPhone (iOS) 上使用 Chrome 或 Firefox 瀏覽器時，收到的簡訊驗證碼 (OTP) 無法自動帶入填寫格（會全部擠在第一個格子），但使用 Safari 瀏覽器則正常。
- **相機權限相容性 Bug**：思報創旭在網頁端測試時，使用小米 12 Pro 掃 QRcode 拍攝印章上傳，系統無法成功調起相機（而一般 PC 與其他手機正常），這屬於 Android 系統特定機型網頁相機權限的相容性問題。
- **第三方信件服務維護導致之延遲**：房屋租賃鄭先生與台灣奇恭 (GiGO) 皆曾反映客戶收不到合約信件或延遲的狀況，後查明為 Mailjet 伺服器維護所致。好好簽隨後提升了自身的硬體效能，以改善此類通訊服務延遲帶來的負面體驗。
- **編輯器與簽署功能 Bug 修正**：針對視界數位整合與富邦國際的反饋，系統修復並上線了多項重要問題，包含「上傳印章手動拖拉等比例縮放」、「自我簽署文字框對齊與複製」、「自我簽署核取方塊形變」，以及「使用分享連結功能時，到期期限強制為 1 天而非發起人手動設定天數」之 Bug。
- **Cookie 快取導致的登出 Bug**：視界數位整合在操作「套用標籤」時，曾因權限不足而被系統自動登出。確認為 Cookie 紀錄快取所致，清除 Cookie 後即回復正常。
- **掃描檔解析度過高 (600 dpi) 導致上傳 timeout 的處理**：2025H2 客戶反映上傳 PDF 失敗或變得很慢，後查明為其掃描檔解析度過高 (達 600 dpi) 導致檔案極大。好好簽目前提供業務引導客戶「將掃描檔降低解析度至 300 dpi 後再轉為 PDF 上傳」 the Workaround 方案。
- **舊注音輸入法搜尋 Bug**：客戶使用舊注音輸入法直接在搜尋框輸入公司名稱會導致無法搜尋到的 Bug。經 Kt 重現並判斷為：舊注音輸入法在選字時即會觸發搜尋，而選完字後反而沒有重新觸發。已修正為「選完字才送出搜尋」的防抖/防錯邏輯。
- **簽名移位之 Bug 修正**：2025H2 部分行政主管反映使用同一份 PDF 範本發起任務，若合約沒有放大，回簽時簽名仍然會跑掉（移位）。
- **核取方塊的呈現樣式 Bug**：客戶反饋在核取方塊勾選完成後，在產出的合約 PDF 中呈現的是「實體方塊」而非「打勾」符號，導致內部人員審核困難（需要呈現為打勾符號）。
- **AWS 備援評估**：針對高可用性與系統備援，好好簽 R&D 與 Hank 召開會議並已安排評估將整個服務遷移或備份於 AWS 之可行性。

### 9. 通路生態系嵌入與 MCP 開放框架

隨著鼎新等通路夥伴逐步成熟，BZS 的 API 設計需要支援「通路多租戶」情境：
- **專屬方案費用客製**：如鼎新平台採 $3,000/年 + $30/份的基礎套裝，和直售客戶的報價體系不同
- **中台化設計方向**：鼎新已預告未來將採「**業務中台**」模式，開放 **MCP (Model Context Protocol) 框架**供各廠商自行開發電子簽章元件並上架，這對 BZS 的 API 文件品質與 SDK 設計提出更高要求
- **百加需求：No-Code 元件化**：百加表達希望 BZS 的電子簽核能做成在**表單設計時不需 Coding 就可使用的現成元件 (No-Code component)**，指向低代碼/拖拉拽整合的需求方向

### 10. 電子印章合規紅線（新）

醫美診所（采盟數位 × 美力時尚診所）要求以「電子印章」取代醫師的「手寫簽名」，BZS 內部評估後**建議拒絕**，理由：
- 電子印章易產生**「諮詢師代替醫師簽名」**的資安合規疑慮
- 在醫療場景下，手寫簽名/生物特徵簽名的身分不可否認性至關重要
- 此決策確立了「**電子印章不能用於需要自然人身份認定的場景**」的合規紅線

### 11. 帳號權限管理與 UX 的衝突（新）

「天選派送」的案例凸顯了 SaaS 平台在帳號管理上的兩難：當企業邀請員工加入為「成員」時，系統出於資安考量要求員工點擊邀請信註冊，但這卻造成了使用者的理解門檻與操作中斷 (UX 衝突)。未來需要思考如何在此類 B2B2E (Employee) 模式中，提供更順暢的無密碼登入或 SSO 整合方案，來降低帳號開通阻力。

**2024H2 新增洞察**：
- **組織架構集中管理權限**：觀察到 B2B 企業在組織架構管理上的盲區，例如主帳號只能看到自己發出的合約，無法統整檢視子帳號發起的合約與聲明錄影檔案。這反映了早期產品在「多帳號權限集中管理」上的設計不足。
- **方案到期與降級權限鎖定衝突**：禮黛與華毅國際案例凸顯了計費系統的 UX 漏洞。方案到期後，系統因為鎖定權限而拿掉了「組織管理」選項，使企業 Admin 帳號無法自行刪除多餘的子帳號，進而無法直接線上改訂人數較少的專業版。在華毅國際案中，客服甚至需要請研發 Hank 於後台手動刪除子帳號，客戶才得以改訂。此外，降級時「子帳號所擁有的歷史合約資料是否強制回歸主帳號」也面臨客戶實務管理偏好的政策衝突（客戶不希望檔案全部回歸主帳號）。這顯示計費到期鎖定機制需更具彈性。
- **離職人員子帳號的合約刪除 Bug**：育達補習班案例中，在管理員試圖變更或刪除已離職員工的子帳號時，因該子帳號下仍存有進行中或未完成的合約，導致系統噴出 500 錯誤。
- **主帳號異動審核機制與法律效力防線**：雅德思生醫案例中，註冊主帳號的員工離職且郵件信箱被公司停用，導致主帳號無法登入或修改。為了防範「後台直接變更主帳號信箱可能影響歷史合約法律效力與軌跡效力」的疑慮，研發與客服專門制定了嚴格的「會員帳號變更申請流程」（個人需檢附雙證件影本與簽名；公司需檢附統編、大小章與申請書，並含個資蒐集聲明），需經 Jessie 審核、Alex/Hank/客服會簽後始能由後台修改。
- **企業版 Admin 下載聲明錄影 UX 盲區**：蔡慶祥律師反饋，企業版的 Admin 帳號在下載子帳號完成的合約時，找不到如何下載「聲明錄影」檔案的入口。建議在子帳號列表右側的操作選項中，直接新增並列的「下載聲明錄影」按鈕，方便客戶一鍵下載。
- **範本統一集中管理機制**：雅居廚櫃等企業客戶提出「子帳號不應能自行建立範本，而應由主帳號統一建立、管理並分享子帳號使用」的權限限制需求。對此，好好簽在後台新增並支援了「範本由主帳號統一管理」之功能設定。
- **公開表單寄送副本給簽署人的自訂設定**：為了滿足部分客戶（如中華民國觀光領隊協會）希望公開表單填寫完後能自動寄送副本給簽署人，而另一部分客戶不需要此功能的差異，好好簽內部評估後計畫於公開表單內提供一個「寄送副本給簽署人」的可勾選選項，供發起人自行設定，該功能已排入後續改版。

### 12. 政府跨境合規認證與技術標準對接（新）

工研院「電子簽章國際接軌子計畫」（2026/5）帶來兩個新興需求維度：
- **DSS 技術標準自我檢測**：工研院參考歐盟 DSS 開源工具開發台灣版技術檢測工具，要求 BZS provide 「平台簽章樣本」供技術檢測，未來能量登錄許可的 TSP 須通過此工具的自我檢測。這意味著 BZS 簽章格式需符合國際技術標準（XAdES、PAdES 等），並具備提供標準化樣本文件的能力。
- **院內整合型 AIO 場域（恩主公醫院）**：護理單位提案在大廳設置整合型簽署平台，需介接醫院 HIS 系統（調閱藥物查詢、手術/自費同意書），並結合院內錄影功能完成簽署，硬體需採大尺寸 AIO 設備以利高齡者使用。此場域模型代表「硬體 + 系統整合 + 電子簽章」三合一的醫療機構整包方案需求。

### 13. 商業模式創新與客製化邊界（新）

2024H2 浮現的幾個特殊商業模式與流程需求：
- **單向強制合約 (不留底)**：如行銷貸款業 (三信國際)，委託代辦貸款合約簽署後，連結即失效，使用者無法保存與瀏覽，藉此保障公司權益（避免拿著合約找別家）。
- **模組化加購 (Add-on)**：小型資訊軟體業 (大暘資訊) 即使訂閱低價的專業版，也願意單次高價加購「雲端憑證」，因為其具有自備工商憑證卡的需求。這為 SaaS 定價提供了微服務模組化的可能性。
- **實體硬體免登入串接**：企業內部簽核流程 (麟雲數據) 採購實體手寫簽名板，要求不需登入系統也可驅動簽名板，顯示硬體與 SaaS 結合的深度需求。
- **產品運營與客戶留存 (Customer Success)**：企業方案客戶 (臺灣數位企業總會) 因為感覺不到產品有更新、沒有收到新功能公告，導致黏著度降低而未續訂。這凸顯了「What's New 新增功能頁面」與「主動行銷溝通」是 B2B SaaS 降低 Churn Rate 的關鍵。
- **格式限制 (PDF vs JPG) 流失大客戶**：台灣安露莎案例顯示，由於其進銷存系統不支援 PDF 僅支援 JPG，且該入會同意書非法規合約，故強烈要求簽署完成後能儲存為 JPG 圖片。好好簽因為評估為單一需求，客製化 API 報價 15 萬元高於客戶預算，最終放棄該需求，導致客戶流失至已支援此功能的競品「叡揚資訊」（其報價低且 2 週內可導入）。
- **CLM 與金流 (Payment) 的一體化需求**：長虹國際顧問案例顯示，許多代理/顧問公司希望將「合約簽署」與「金流收取 (如 Stripe、綠界)」在同一個電子化流程中完成，代表電子簽章向 CLM 發展時，金流串接是不可或缺的加值服務。
- **現場簽功能下放到專業版**：休閒運動潛水業者整年有超過 1000 人需現場簽風險聲明書，但企業方案 (NT$1500/月) 超出其小微企業預算。好好簽內部研擬將「現場簽」功能下放到專業版，以搶佔該高頻次、低預算的小微企業市場。
- **合約作廢的標籤 Workaround**：麟雲數據反映簽署完畢後若發現內容錯誤想要修改，但系統不允許刪除已完成的合約。客戶被迫採用建立「作廢」標籤來管理，這顯示了 CLM 對於合約生命週期中「作廢/修改/版本更迭」機制的原始需求。
- **合約刪除之法規合規性紅線**：育達補習班反映，簽署完畢後若發現合約內容錯誤想刪除測試資料，好好簽答覆：「不允許刪除已簽署之合約」，因為系統無法區分「測試」或「正式」合約，且在電子簽章法律合規與生命週期審計軌跡完整性上，合約刪除功能存在灰色地帶。
- **Videosign 競品的 Usage-based (按量付費) 定價模式威脅**：GCIT 競品評估案例顯示，國外競品 Videosign 除了具備「邊簽邊錄（雙鏡頭錄人臉與手部動作）」外，採用「基本底費 + 合約數量」的按量付費模式，對於用量少但有大企業品牌需求的客戶而言，比起好好簽純月租（企業版）更具價格吸引力。

### 14. 範本編輯器與簽署端 Onboarding 最佳實務（新）

- **簽署端的低阻力引導 (Onboarding Flow)**：實務反饋指出，雖然發起人熟悉系統，但許多消費者在首次收到合約時，因不知如何點擊簽署而作廢。系統為此規畫「在簽署連結開啟時，預設顯示操作教學影片」，以降低簽署端的流失率。
- **編輯器樣式與欄位群組化**：為了使合約條款排版精美，TNL 與安露莎等客戶強烈要求範本編輯器文字欄位能支援 **「粗體、下底線、文字顏色」** 等樣式設定，以及支援 **「欄位群組 (Group)」**，使姓名、電話、地址能統一群組排版。
- **大章小章去背合併 (Workaround)**：圓夢傳媒因擁有兩家公司，但專業版限制只能上傳 1 個印章。客戶被迫將大章與小章蓋在同一張紙上，拍照去背後上傳成單一圖檔，作為規避印章數限制的實務 workaround。這顯示大企業在多品牌管理時對印章數量的剛性需求。
- **核取方塊與選擇鈕的大小調整限制**：貳輪嶼股份有限公司反映，目前範本編輯器中，「核取方塊」與「選擇按鈕（單選鈕）」無法調整大小，在合約中顯得與文字大小不協調，極度影響美觀。
- **文字設定置中對齊需求**：興達會計師事務所案例中，客戶反映範本編輯器的文字欄位不支援置中，尤其在金額填寫格（萬、仟、百、拾、元整）時極為不便。
- **股東簽到簿的多欄位表單規格**：興達會計師事務所因有大量股東會召開需求，提出 Power Form 支援包含編號、股東戶號、股東姓名、持有股數、簽名、委託人簽名等多欄位的股東簽到簿格式。Kevin 已著手規劃相關規格。

## 總結
從好好簽 (BZS) 的業務前線數據可以明確看出，台灣電子簽章市場的決戰點已不再是「簽名介面好不好看」，而是這套系統能不能**「無縫隱形在企業既有的系統流程中（API）」**、**「符合台灣人的通訊習慣（LINE/SMS）」**，並在**「法規安全與使用體驗間取得平衡」**。

值得注意的是，這類對「內網資安、地端備援與 AD 深度整合」的強烈需求，也正是具有資安背景的競品（如全景軟體的 FastSIGN Pro）所主打的市場。SaaS 服務商在爭奪大型本土客戶時，如何在雲端架構下滿足這類近乎「地端客製化」的嚴苛要求，將是勝出的關鍵。

**2026 年 5 月新增洞察**：鼎新 MCP 中台化方向，顯示通路夥伴正在由「系統整合商」升級為「平台生態系建設者」。BZS 若要在此生態中取得有利位置，需盡快完善 API 文件、SDK 與認證機制，以降低第三方開發者的接入門檻。

用 Claude Code （或者 OpenCode） + Skill 搭建 AI 开发流程 - 从想法到可运行项目
Vibe Coding 火了之后，很多人都想用 AI 写代码，但真正动手就发现问题：需求没想清楚就开始写，写到一半发现方向不对；不给设计稿让 AI 自由发挥，出来的界面丑得没法看；改了几轮代码，文档还是最初的版本，下次打开项目完全想不起来改过什么。
所以我们用 Claude Code 的 Agent + Skill 功能搭建了一套开发流程，核心思路是把产品经理、UI 设计、全栈开发的方法论分别写进三个 Skill，让 AI 按照专业标准去收集需求、生成原型、实现代码。你只需要说出想法，剩下的需求追问、文档生成、原型设计、代码开发就自动完成。
整体架构是一个主控加三个技能：毒舌产品经理负责需求收集，UI 提示词设计师负责原型图提示词，全栈开发工程师负责代码实现。流程按顺序推进——先通过追问把需求想清楚，生成产品文档；再根据文档生成原型图；然后开发代码；最后本地运行。每次新增或修改功能，产品经理都会先更新文档，再交给开发实现，确保文档和代码始终同步


---
核心功能模块
毒舌产品经理：逼你想清楚
很多项目失败不是技术问题，是一开始就没想明白要做什么。这个技能的核心就是通过追问把需求漏洞堵上。它不会接受「大概」「可能」这种模糊回答，发现逻辑矛盾会直接指出，发现你在自嗨会泼冷水。同时它会主动建议 AI 增强——你设计了繁琐的手动流程，它会问「这里要不要让 AI 来做」。

0-1 模式和迭代模式自动切换
系统启动时会自动检测项目状态。没有产品文档就进入 0-1 模式，从头开始收集需求；有产品文档就进入迭代模式，直接接住你的修改需求往下问。迭代模式会自动检测新需求和现有文档的冲突，发现问题直接指出并给解决方案。你不需要告诉它现在是什么阶段，它自己判断。

UI 提示词设计师：省掉设计环节
需求确定后，这个技能会根据产品文档自动生成原型图提示词。你把提示词丢给 Midjourney 或 Gemini，就能拿到设计稿。省掉了自己写提示词或找设计师的环节，而且生成的原型图和需求文档是对应的，不会出现「设计和需求不一致」的问题。

全栈开发工程师：一条龙实现
拿着需求文档和原型图，它会判断项目类型、选择技术栈、搭建项目结构、实现功能代码。支持 /run 本地运行、/check 对照文档检查功能完整度。如果有遗漏，它会列出来并补充。

主控调度：流程自动衔接
三个技能不是各干各的，由主控文件统一调度。你说想加个功能，它会先调用产品经理更新文档，再调用开发去写代码。你说想生成原型图，它会先检查有没有产品文档。流程之间的衔接是自动的，你不需要手动切换。

注：这套方案能快速完成从想法到可运行代码的全流程，但不要期待一步到位的完美结果。生成的代码是起点，不是终点——你仍然需要根据实际运行效果去调整、优化、迭代。另外，这套流程涉及需求理解、文档生成、代码实现的多轮协作，对模型的理解和推理能力要求比较高，建议使用 Claude Opus 或 GPT 5.2 级别的模型。模型能力和输出质量是正相关的，用更强的模型，生成的文档和代码质量也会更高。

在 Claude Code 中配置
请按照以下步骤配置开发流程系统，配置完成后，你的项目结构应该是这样：
project/
├── Product-Spec.md                      # 产品需求文档（自动生成）
├── Product-Spec-CHANGELOG.md            # 变更记录（自动生成）
├── UI-Prompts.md                        # 原型图提示词（自动生成）
└── .claude/
    ├── CLAUDE.md                        # 主控配置（必须创建）
    └── skills/                          # 技能包（必须创建）
        ├── product-spec-builder/        # 产品经理技能包
        │   ├── SKILL.md
        │   └── templates/
        │       ├── product-spec-template.md
        │       └── changelog-template.md
        ├── ui-prompt-generator/         # UI 提示词设计师技能包
        │   ├── SKILL.md
        │   └── templates/
        │       └── ui-prompt-template.md
        └── dev-builder/                 # 全栈开发工程师技能包
            └── SKILL.md

创建主控配置
1. 在 .claude/ 目录下创建 CLAUDE.md 文件
2. 粘贴主控角色定义、工作流程、指令集
3. 包含项目状态检测、技能调用规则、四个阶段的流程定义（需求收集 → 原型设计 → 项目开发 → 本地运行）

创建产品经理技能包
4. 在 .claude/skills/ 目录下创建 product-spec-builder/ 文件夹
5. 创建 SKILL.md 定义毒舌产品经理角色、追问策略、0-1 模式和迭代模式的切换逻辑
6. 在 templates/ 下创建 product-spec-template.md 定义产品文档输出格式
7. 在 templates/ 下创建 changelog-template.md 定义变更记录格式

创建 UI 提示词设计师技能包
8. 在 .claude/skills/ 目录下创建 ui-prompt-generator/ 文件夹
9. 创建 SKILL.md 定义提示词生成规则、视觉风格选项、配色方案
10. 在 templates/ 下创建 ui-prompt-template.md 定义提示词输出格式

创建全栈开发工程师技能包
11. 在 .claude/skills/ 目录下创建 dev-builder/ 文件夹
12. 创建 SKILL.md 定义技术栈选择策略、项目初始化流程、代码实现规范

重要配置细节
- 技能调用规则：CLAUDE.md 定义了调度规则，需求收集调用产品经理，原型设计调用 UI 设计师，代码开发调用全栈工程师
- 模式自动切换：启动时自动检测 Product-Spec.md 是否存在，没有进入 0-1 模式，有则进入迭代模式
- 循环配合机制：每次新增或修改功能，先调用产品经理更新文档，再调用开发实现代码，确保文档和代码同步
- 模板约束：templates/ 中的格式是强制性的，所有输出必须按照模板结构
- 文档驱动：所有产物写入项目根目录，对话中断后可通过 /status 恢复进度
- 指令集：支持 /prd（需求收集）、/ui（生成原型图提示词）、/dev（开发代码）、/run（本地运行）、/check（检查完整度）

工作流程
1. 说出想法 — 告诉 AI 你想做什么产品
2. 需求收集 — /prd 产品经理通过追问完善需求细节
3. 生成文档 — 自动生成 Product-Spec.md 和 CHANGELOG
4. 原型设计 — /ui 根据产品文档生成原型图提示词
5. 生成原型图 — 把提示词发给 Midjourney 或 Gemini 生成设计稿
6. 前端开发 — 用 Google AI Studio Builder 开发前端
7. 后端改造 — /dev 把前端代码改造成前后端分离项目
8. 本地运行 — /run 启动项目，验证功能
9. 功能迭代 — 提出修改需求，产品经理先更新文档，开发再实现代码
10. 完整度检查 — /check 对照产品文档检查功能是否遗漏

关键特性
- Agent + Skill 解耦 — 主控负责调度，技能负责专业能力，可独立替换
- 0-1 和迭代模式自动切换 — 启动时检测产品文档是否存在，自动进入对应模式
- 毒舌追问机制 — 不接受模糊回答，发现逻辑漏洞直接指出，逼用户想清楚
- 循环配合流程 — 每次修改先更新文档再写代码，文档和代码始终同步
- 模板约束 — 严格遵循 templates/ 定义的格式，保证输出规范统一
- AI 增强建议 — 产品经理会主动建议用 AI 简化繁琐的手动流程
- 冲突检测 — 迭代模式下自动检测新需求和现有文档的冲突
- 文档驱动 — 所有产物写入文件，对话中断后可通过 /status 恢复进度
- 项目状态检测 — 启动时自动扫描目录，检测进度并路由到对应阶段

模型选择说明
这套方案依赖 Claude Code 的 Agent + Skill 功能来实现自动化开发流程。如果你用不了 Claude Code，也可以在 OpenCode 中使用，模型可以选择 GPT 5.2。
需要注意的是，不同模型在理解需求、执行复杂指令、生成高质量代码等方面的能力存在差异。从实测效果来看：
- 理解能力：模型对用户需求的理解深度会影响产品文档的质量，比如能否准确识别核心功能、判断功能优先级、发现需求漏洞
- 执行能力：模型遵循模板格式、按照技能定义执行任务的严格程度会影响输出质量
- 代码质量：模型在生成代码时的规范性、可读性、错误处理能力会影响最终项目的可用性
- 多轮协作：模型在产品经理和开发工程师循环配合过程中保持上下文一致的能力会影响迭代效率
建议选择支持长上下文的模型。初次使用时可以先用一个简单项目测试效果，确认该模型能否满足你的质量要求，再进行复杂项目。如果发现生成内容偏离预期较多，可以尝试更换模型或调整配置。

核心功能模块
八个 Skill 作为前馈引导（Guides）
Harness 的前馈控制是在 Agent 行动之前就把标准和方法论注入进去，提高一次做对的概率。这套系统把产品开发拆成八个阶段，每个阶段对应一个独立的 Skill：
product-spec-builder 负责需求收集。不是让你写一份需求文档扔给 AI，而是反过来——AI 通过多轮追问帮你把模糊的想法变成结构化的产品需求。你说"我要做一个写小说的工具"，它会追问：只支持一种题材还是多种？交互方式是对话式还是编辑器？项目管理怎么做？问到你自己都没想过的细节，问完了帮你生成一份面向 AI 的 Product Spec——这份文档不是给人看的，是给后续所有 Skill 当执行基准的。需求变更时进入迭代模式，更新 Spec 的同时自动生成变更记录。
design-brief-builder 负责设计规范。你说"深色主题、极简风格"，AI 可能给你搞出十种完全不同的理解。这个 Skill 通过追问把视觉方向量化——配色方案、点缀色性格、文档结构、交互元素风格、动效级别——输出一份 Design Brief，让后续的设计和开发有统一的视觉标准可以对齐。
design-maker 负责设计图制作。通过 Pencil 或 Figma 的 MCP 连接，直接在设计工具中生成完整的页面原型图。这一步的产出在整个流程中权重最高——后面写代码时，AI 优先参照设计图，其次是设计规范，最后才是需求文档。没有设计图的 Vibe Coding，出来的东西大概率不好看。
dev-planner 负责开发计划。读完需求文档、设计规范和设计图后，先上网调研涉及的技术栈有没有现成组件可以用，然后把整个项目拆成多个 Phase，每个 Phase 有明确的交付内容。这份 DEV-PLAN 不仅是给 AI 的开发指南，也是跨 session 接续开发的进度锚点——新开一个对话，AI 读一遍 DEV-PLAN 就知道从哪继续。
dev-builder 负责项目开发。不是一口气把整个 Phase 写完，而是拆成多个 Task 逐个完成。每完成一个 Task，先编译验证确保没有报错，再进入下一个。出了问题能精确定位是哪个 Task 引入的，不用在一大堆代码里翻找。
bug-fixer 负责修 bug。后面单独展开。
code-review 负责代码审查。两阶段审查——Stage 1 查功能完整性（Spec 逐条对照代码，有没有漏实现的、有没有多做的），Stage 2 查代码质量（命名、类型、结构、安全）。Stage 1 有 HIGH priority 问题就停在 Stage 1，不往下走。
release-builder 负责构建发布。
四阶段系统性调试——不猜不试的 Bug Fixer
这个 Skill 值得单独说。它不是那种看到报错就试着改的方式，而是一套医生诊断式的调试流程。
第一阶段收集证据：读完整的错误信息和 stack trace，复现 bug 确认是稳定还是偶发，检查最近的代码变更，追踪数据流从触发点到报错点经过了哪些函数。第二阶段分析模式：找到正常工作的相似功能做对比，识别差异和可疑之处。第三阶段假设验证：基于证据形成最多 3 个假设，按可能性排序，用最小改动验证最可能的假设，假设被否定就记录原因换下一个。第四阶段实施修复：一次只改一个逻辑点，改完编译验证、功能验证、回归验证。
核心原则是不猜不试。没有证据就不下结论，一次只改一个地方——同时改多处无法判断哪个是真正的修复。改完还要回归验证，确保修了 A 不会坏 B。
另一个关键规则：同一个 bug 反复修了多次还没好，就停下来重新审视问题本身——可能不是代码层面的问题，可能是架构问题、环境问题或理解偏差。不硬磕。
Review → Fix 闭环——最重要的推理型传感器（Inferential Sensor）
Harness 里的传感器分两种：计算型的（Hook 脚本，确定性，跑得快）和推理型的（用模型做判断，非确定性，但能做语义级检查）。两阶段 Code Review 就是最重要的推理型传感器——它不只是看编译过不过，而是让一个独立的 reviewer Agent 去理解代码和需求的关系。
代码不是写完就算，写完必须过审。流程是这样的：
功能开发完成 → 派发 code-reviewer 执行两阶段审查 → Stage 1 通过进入 Stage 2，Stage 1 失败补实现后重新审查 → Stage 2 通过则自动 commit + push，Stage 2 失败调用 bug-fixer 修复后重新审查 → 循环直到两个 Stage 都通过。
这个循环是自动的，不需要你手动触发。每完成一个 Task 就跑一遍，不是攒到 Phase 结束才审。Phase 结束时还有一轮更高层级的验证——跨 Task 的集成检查、测试完整性、编译验证、功能测试——发现问题再修再提交。
Sub-Agent 隔离——上下文防火墙（Context Firewall）
执行层有四个 Sub-Agent：implementer 负责编码，code-reviewer 负责审查，feedback-observer 负责记录反馈，evolution-runner 负责扫描进化建议。
这里有一个关键的设计原则：每个 Task 都用一个全新的 Sub-Agent 实例，不复用、不继承之前的上下文。为什么？因为如果让 Agent 带着前一个 Task 的记忆去做下一个 Task，前面的错误假设就可能污染后面的判断。主 Agent 给 Sub-Agent 的任务包里包含完整的上下文——Spec 条目、交付清单、涉及文件、项目结构——但不包含之前 Task 的执行历史。隔离才能保证每个 Task 的执行是干净的。
Hook 作为反馈传感器（Sensors）
Harness 的另一半是反馈控制——Agent 行动之后检查结果，发现偏差就触发修正。光靠 Skill 里的自然语言规则让 AI 自己决定什么时候该做什么，是不够靠谱的。AI 有时候会"忘记"审查代码就准备收工，有时候会"觉得"之前读过文档就不再重新读。所以我们设计了六个 Hook 脚本在关键节点自动触发，作为确定性的传感器，不依赖模型的判断。
pre-commit-check：每次 commit 之前自动跑编译检查。编译不过，commit 直接被阻止——带着错误的代码提交不上去。
auto-push：commit 成功后自动推送到远程仓库，不用手动操作。
stop-gate：Agent 准备停下来的时候检查——代码改了但还没做 code review？不让停，必须先审查完。这个 Hook 解决了一个真实问题：AI 有时候写完代码就觉得任务完成了，但按流程必须先过审才能结束。
detect-feedback-signal：自动检测你的消息里有没有修正或不满的关键词——"你搞错了"、"不是这样"、"你又忘了"——检测到就提醒主 Agent 记录反馈。反馈记录是半自动的，很多时候你不需要专门说"记下来"，系统自己就会捕捉到。
mark-review-needed：代码文件被编辑或创建后，自动标记为"需要 review"。配合 stop-gate 使用——只要有代码变更，就不能跳过审查。
check-evolution：每次新开 session 时检查 feedback 积累，有待处理的就提醒。
进化系统作为方向盘迭代（Steering Loop）
Harness 不是搭完就不动了。好的 Harness 会从使用中学习——每次出问题，你不是去修模型，而是去改 Harness，让同样的错不再发生。这就是 Steering Loop，也是这套方案和一次性 prompt 方案的本质区别。
进化分四层。第一层，你给反馈时，feedback-observer 静默记录，你几乎无感。第二层，同一条反馈出现三次以上，evolution-runner 会提议把它升级为写进 Skill 的正式规则——比如"每个 Phase 开始时必须重新读文档"这条，如果你反复提醒过三次，它就不再是临时记忆，而是永久规则。第三层，某个 Skill 的反馈评分持续偏低，系统提议优化这个 Skill。第四层，某种操作模式反复出现但没有 Skill 覆盖，系统提议创建一个全新的 Skill。
整个过程对你是无感的——记录和扫描都在后台完成，只有产生了具体建议才会轻轻提示你。而且每条建议都需要你确认才会执行，绝不自动改规则。
设计优先级——设计图是最高权威
整套系统有一条明确的视觉参照优先级：设计工具中的设计稿（最高）→ Design-Brief.md（次之）→ Product-Spec.md（功能逻辑）。有设计图时，一切 UI 以设计图为准，冲突时设计图优先。
这也是为什么我们会有一条 feedback 记录——"新增或修改 UI 功能时必须同步更新设计稿"。你加了一个右键菜单功能，更新了 Spec 和代码，但忘了更新设计图。设计图不包含这个功能，后续 code review 对照设计图就会遗漏它，形成盲区。所以 UI 变更的检查清单是：更新 Spec → 更新设计稿 → 更新 DEV-PLAN → 实现代码 → review 时对照设计稿验证。
注：这套方案能大幅减少从想法到可运行产品的人工管理成本，但不要期待一步到位。一个完整产品不可能一个 session 跑完，你需要不断开新 session——DEV-PLAN 就是跨 session 接续开发的锚点。上下文一长，AI 的记忆会被挤掉，所以每个 Phase 开始时都要让它重新读文档，这个习惯很重要。另外，设计图这一步目前依赖 Pencil 或 Figma 的 MCP 连接，需要你的设计工具支持 MCP 协议。

模型选择说明
这套方案基于 Claude Code 的 Agent + Skill + Hook 功能。Harness Engineering 的一个核心洞察是：同样的模型，在不同质量的 Harness 下，任务完成率有决定性区别。但 Harness 再好，模型能力仍然是底线——由于覆盖了产品开发的完整链路，对模型能力的要求比单一任务方案更高：
- 需求理解：模型通过追问提炼需求的能力，直接决定 Product Spec 的质量——追问不到位，后续所有环节都在错误的基准上执行
- 设计执行：模型理解设计规范并通过 MCP 操作设计工具的能力，决定设计图的还原度
- 编码质量：模型遵循 DEV-PLAN 和设计稿编码的严格程度，决定每个 Task 的完成度
- 调试能力：模型按四阶段调试法定位根因的能力，决定 bug 能否一次修好而不是越修越多
- 审查精度：模型按两阶段审查清单逐项检查的判断力，决定 code review 能否真正把住质量关
- 进化识别：模型从用户反馈中提取可泛化规则的能力，决定进化系统能否真正沉淀有价值的经验
建议使用 Opus 或 Sonnet 级别的模型。Sub-Agent 每个都是独立的上下文，token 消耗会随 Task 数量增长。初次使用建议先用一个小项目跑通全流程，确认产出质量和工作流顺畅度，再投入完整项目。
